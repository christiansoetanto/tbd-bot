- 2026-08-03: Outage. The bot was dead in Discord for ~33 hours — `tbd_bot_handler_duration_seconds_count{handler="cm_question_limiter"}` froze at 449 on 08-01 19:00 UTC — while the container reported `healthy` the whole time. The `BOTTOKEN` had been reset, so REST calls returned 401 and the gateway could not re-identify. Two things hid it. And the container's env was frozen at its 07-29 05:56 creation: both `.env` files were edited hours later, but 31 `docker restart` calls never re-read `env_file`, so the container ran a stale `GITHUBAPITOKEN` and failed GitHub with `Bad credentials` from 07-30 — Office of Readings pushed nothing for four days. Only `docker compose up -d --force-recreate` picks up `.env`. Recovered by regenerating the token into both `.env` files and recreating. One loose end left unchased: the container logged 32 starts between 07-29 and 08-01 (`RestartCount=31`) with `OOMKilled=false`, cause unknown. It is 0 since the recreate, so it was not pursued.

- 2026-08-03: Closed the monitoring gap the outage exposed. Liveness now comes from discordgo's `LastHeartbeatAck` rather than from a flag a handler has to clear: a boolean set by the `Disconnect` event cannot see an identify that never succeeds or a wedged goroutine, and would have stayed at 1 through the whole outage. `GatewayStaleAfter` is 3 minutes, about three missed 41s beats, which tolerates an ordinary reconnect — discordgo logged two on 08-02 while the bot was already dead, so `Disconnect` alone is far too noisy to gate health on. `/health` returns 503 past that window and the Docker `HEALTHCHECK` probes it instead of `/metrics`; `/metrics` deliberately stays unconditional, since a metrics endpoint that fails during an incident destroys the series needed to alert on it. New metrics: `tbd_bot_discord_connected`, `..._last_heartbeat_ack_timestamp_seconds`, `..._heartbeat_latency_seconds`, `..._gateway_events_total`, and `tbd_bot_external_api_failures_total{api,reason}`. That last one supersedes the `tbd_bot_github_api_failures_total` named in the old open question below — one vec covers GitHub and Discord, and `HTTPFailureReason` collapses status codes to a fixed label set so a misbehaving upstream cannot grow the series count.

- 2026-08-03: Grafana alerting provisioned in `grafana/provisioning/alerting/`, delivering to a Discord webhook from `GRAFANA_DISCORD_WEBHOOK_URL`. Webhook over email: no credentials, no spam filtering, and independent of `BOTTOKEN` and the bot process, so it survives the failure it reports. Verified end to end with a temporary canary rule rather than assumed — `grafana_alerting_notification_requests_total{integration="discord"}` reached 1 with no failures, which also proves `$__env{}` interpolation resolved, since a literal `$__env{...}` string is not a valid URL and would have errored. Two traps found while doing it. Deleting a provisioned rule's file does not delete the rule: Grafana copies it into its own database and keeps it, exactly like `GF_SECURITY_ADMIN_PASSWORD`, and removal needs an explicit `deleteRules` directive. And the gateway and target rules use `noDataState: Alerting` on purpose — every signal that failed on 08-01 failed by going quiet, so a rule treating absence as health would reproduce the outage it exists to catch.

- 2026-08-03: Settled which `.env` compose actually reads, which the outage investigation could not discriminate once all three copies matched. A sentinel line added only to `~/tbd-bot-secrets/.env` does not appear in `docker compose config`: compose reads the repo `.env` and nothing else. The secrets file reaches deploys solely because `deploy.yml` runs `cp ~/tbd-bot-secrets/.env .env` first, making the repo `.env` a deploy artefact rather than a second source of truth. This matters most for Grafana, which has no `env_file` and gets `GRAFANA_DISCORD_WEBHOOK_URL` only through `${...}` interpolation — unset, it resolves to an empty string and alerting provisions cleanly while delivering nowhere. `deploy.yml` was checked and needs no change: it composes the whole stack unnamed, so Grafana is recreated and picks up alerting, and its health gate reads `docker inspect .State.Health.Status`, which now follows the gateway. `TestDeployWorkflow` gained a guard against narrowing that command to `... --build tbd-bot`, which would still deploy the bot while quietly stranding the alerting config on whichever machine last ran compose by hand.
